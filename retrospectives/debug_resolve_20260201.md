# 🚀 SQLite 로컬 캐싱 도입을 통한 채팅 성능 혁신 및 지표 정량화

> **Project:** CSHCHATAPP (Side Project)  
> **Topic:** SQLite 도입 전/후 성능 측정 및 UX 일관성 확보  
> **Tech Stack:** React Native, SQLite, Firestore, TypeScript

## 1. 배경 및 문제 상황 (Background & Problem)

기존 Cloud DB(Firestore) 중심의 데이터 구조에서 다음과 같은 사용자 경험(UX) 및 기술적 한계 직면.

- **성능 가변성 (Volatility):** 네트워크 상태에 따라 메시지 로딩 속도가 최소 150ms에서 최대 535ms까지 큰 폭으로 변동되어 일관된 UX 제공 불가.
- **높은 레이턴시:** 사용자 인지 한계선(100ms)을 상회하는 로딩 시간으로 인해 채팅방 진입 시 '답답함' 유발.
- **오프라인 제약:** 네트워크 단절 시 기존 대화 내역 확인이 불가능하여 서비스 신뢰도 저하.
- **운영 효율성 결여:** 동일 데이터 반복 Fetch로 인한 Firestore 읽기 비용(Read Count)의 비효율적 증가.

## 2. 해결 과정 (Problem Solving Process)

### 이슈 1: 정량적 성능 지표 측정 시스템 구축

**A. 해결책**
비동기 및 동기 작업의 실행 시간을 정밀 측정하고 통계를 산출하는 커스텀 훅(`usePerformanceMeasure`) 개발. `FIRESTORE_FETCH`, `SQLITE_SAVE`, `FETCH_CHAT_MESSAGES` 등 주요 체크포인트에 래핑하여 데이터 수집.

**B. 효과**

- 막연한 "더 빨라졌다"는 체감이 아닌, 수치 기반의 명확한 개선 근거 확보.
- 네트워크 레이턴시와 DB I/O 레이턴시를 분리 분석하여 병목 지점 파악 가능.

---

### 이슈 2: SQLite 기반 로컬 캐싱 레이어 아키텍처 구현

**A. 해결책**
UI가 항상 로컬 DB를 바라보게 하는 **Single Source of Truth** 전략 채택. 서버 데이터는 로컬 DB를 거쳐 화면에 뿌려지는 `Write-Through` 구조로 설계.

**B. 성능 최적화**

- **복합 인덱스 적용:** `(roomId, seq DESC)` 인덱스 생성을 통해 수만 건 데이터에서도 10ms 이내 탐색 속도 보장.
- **동기화 로직:** `INSERT OR REPLACE` 및 `seq`(시퀀스) 기반 페이징 브릿지를 통해 데이터 무결성 확보.

---

### 이슈 3: UX 일관성 (Deterministic UX) 확보

**A. 의사결정**
네트워크가 빠를 때만 빠른 것이 아니라, 모든 상황에서 일정한 반응성을 주도록 설계.

- **Offline-First:** 네트워크 상태와 무관하게 즉시 로컬 데이터를 렌더링.
- **심리스 페이징:** 스크롤 시 발생하는 지연 시간을 네트워크 통신 단계에서 로컬 DB 쿼리 단계로 단축.

## 3. 성과 및 회고 (Results & Retrospective)

### 수치 기반 성과 요약

| 측정 항목                 | 개선 전 (Firestore) | 개선 후 (SQLite)     | 개선율               |
| :------------------------ | :------------------ | :------------------- | :------------------- |
| **메시지 로딩 (20건)**    | ~286.74ms           | **~9.24ms**          | **약 31배 (3,100%)** |
| **응답 편차 (Stability)** | ±190ms (가변적)     | **±1.5ms (균일함)**  | **매우 높음**        |
| **UX 등급**               | 보통 (기다림 인지)  | **최상 (즉각 응답)** | -                    |

- **회고:** 이번 작업을 통해 '속도'만큼 중요한 것이 '일관성'임을 깨달았습니다. 사용자는 200ms의 빠른 속도보다 10ms의 일정한 속도에서 더 높은 신뢰를 느낍니다. 또한, `usePerformanceMeasure`를 직접 제작하며 데이터 기반의 성능 튜닝이 개발자의 주관을 배제하고 팀을 설득하는 데 얼마나 강력한 도구가 되는지 경험했습니다.
