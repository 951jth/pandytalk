# ⚖️ WebSocket vs Firestore: 전략적 비교 및 엣지 케이스

채팅 시스템 구축 시 기술 스택 선택을 위한 비교 분석과 실제 운영 환경에서의 고려 사항을 정리합니다.

---

## 1. 실시간 통신 방식별 비교 (Trade-off)

| 비교 항목 | Firestore (BaaS) | WebSocket (Push) | HTTP Polling (Pull) |
| :--- | :--- | :--- | :--- |
| **작동 원리** | SDK 내부 스트림 | 양방향 상시 통로 | 주기적으로 서버에 문의 |
| **실시간성** | 상 | 최상 | 하 (주기마다 지연 발생) |
| **서버 부하** | 낮음 (구글이 관리) | 보통 (연결 유지 비용) | 높음 (반복 요청 처리) |
| **데이터 효율** | 보통 | 매우 높음 (헤더 최소화) | 매우 낮음 (HTTP 헤더 중복) |
| **구현 난이도** | 매우 쉬움 | 보통 | 쉬움 |
| **주요 용도** | MVP, 일반 채팅 | 고성능 채팅, 게임 | 대시보드, 알림 체크 |

### 💡 HTTP Polling의 특징
*   **장점**: 웹소켓을 지원하지 않는 아주 오래된 환경에서도 작동합니다. 별도의 소켓 서버 유지 없이 표준 HTTP 서버만으로 구현 가능합니다.
*   **단점**: 메시지가 없어도 계속 물어봐야 하므로 서버 자원과 데이터 트래픽이 낭비됩니다.
*   **Socket.io의 역할**: 처음에 폴링으로 연결을 시도한 후, 가능하면 웹소켓으로 '업그레이드'하고, 실패하면 폴링을 '백업(Fallback)'으로 사용합니다.

### 🏆 최종 선택 가이드
*   **MVP / 초기 서비스**: **Firestore** 추천. 리소스를 아껴 기능을 빠르게 출시하는 것이 중요합니다.
*   **성장기 / 대규모 서비스**: **WebSocket** 추천. 비용 절감과 정교한 운영 기능이 중요해지는 시점입니다.

## 2. Firestore 리스너 비용과 WebSocket 전환 기준

현재 앱의 채팅 메시지 구독은 방 화면 포커스 중 `chats/{roomId}/messages`에 대해 `seq > lastSeq` 조건으로 Firestore realtime listener를 붙이는 구조입니다. 이 방식은 구현과 안정성은 좋지만, 그룹채팅에서는 메시지 1개가 방을 열고 있는 멤버 수만큼 전달되므로 read 비용이 멤버 수에 비례해 증가합니다.

```text
실시간 메시지 read / day
= 하루 메시지 수 × 메시지당 평균 실시간 수신자 수
```

예를 들어 50명이 같은 그룹방을 열고 있을 때 메시지 1개가 생성되면, 각 클라이언트 리스너가 새 메시지 문서를 받으므로 대략 50 document reads가 발생합니다. 푸시 알림 함수의 LRU 캐시는 FCM 토큰 조회 비용을 줄이는 것이므로, 클라이언트 메시지 리스너 read 비용과는 별개입니다.

### Firestore 리스너 유지가 적합한 구간
*   DAU가 수천 명 이하이고 대부분 1:1 또는 소규모 그룹채팅인 경우.
*   동시에 같은 방을 보고 있는 사용자가 많지 않은 경우.
*   Firestore read 비용이 월 예산에서 큰 비중을 차지하지 않는 경우.
*   오프라인 캐시, 재연결, 보안 규칙, 정렬, 동기화의 운영 단순성이 더 중요한 경우.

### WebSocket 검토를 시작할 신호
*   특정 그룹방에 동시 접속자가 자주 50~100명 이상 발생하는 경우.
*   공개방, 이벤트방, 팬덤방처럼 메시지가 매우 많은 방이 생기는 경우.
*   `하루 메시지 수 × 평균 실시간 수신자 수`가 커져 messages listener read가 비용의 주요 원인이 되는 경우.
*   리스너 재연결이 잦아 초기 스냅샷 read가 반복되는 경우.
*   Firestore read 비용보다 별도 realtime server 운영 비용이 더 예측 가능하고 저렴해지는 경우.

### 판단 가이드
*   하루 30만 reads 수준의 실시간 메시지 전달은 Firestore로도 운영 가능한 범위입니다. 다만 상위 그룹방의 비용 추이를 관찰합니다.
*   하루 수백만 reads가 messages listener에서 반복적으로 발생하면 WebSocket 또는 하이브리드 realtime layer를 진지하게 검토합니다.
*   전체 채팅을 한 번에 전환하기보다, 대형/공개/라이브 그룹방만 WebSocket으로 분리하고 1:1 및 소규모 그룹은 Firestore를 유지하는 하이브리드 전환이 안전합니다.

전환 판단 전에 최소한 방별 하루 메시지 수, 방별 평균/최대 동시 접속자 수, `subscribeChatMessages` 유지 시간, Firestore daily read 중 messages listener 비중을 계측합니다.

## 3. 실전 운영 시 엣지 케이스 (Edge Cases)

웹소켓 채팅을 실제 서비스에 적용할 때 반드시 방어해야 하는 시나리오입니다.

### ① 중복 전송 방지 (Idempotency)
*   **상황**: 서버가 DB 저장 후 응답(Ack)을 보내기 직전 네트워크가 끊겨 사용자가 재전송할 때.
*   **해결**: 클라이언트에서 생성한 고유 ID(`clientMsgId`)를 서버에서 체크하여 중복 저장을 차단합니다.

### ② 동기화와 실시간 메시지의 충돌 (Race Condition)
*   **상황**: 재연결 싱크 요청 응답과 동시에 실시간 소켓 메시지가 도착할 때 데이터 순서가 꼬이는 문제.
*   **해결**: 메시지 리스트 업데이트 시 항상 `seq` 번호를 기준으로 중복 체크 및 정렬 로직을 수행합니다.

### ③ 유령 연결 (Zombie Connections)
*   **상황**: 연결은 되어있으나 실제 데이터가 흐르지 않는 '죽은' 상태.
*   **해결**: 하트비트(Ping/Pong) 주기를 관리하여 연결 끊김을 신속하게 감지합니다.

### ④ 대량의 데이터 갭 (Large Gaps)
*   **상황**: 장기 미접속자가 수만 개의 누락 메시지를 한 번에 싱크하려 할 때.
*   **해결**: 누락 개수가 일정 이상이면 소켓 대신 페이지네이션이 적용된 REST API로 유도합니다.

### ⑤ 토큰 만료 처리 (Token Expiration)
*   **상황**: 연결 도중 JWT 토큰이 만료되어 보안 위협이 발생할 때.
*   **해결**: 서버가 만료 감지 시 `auth_error`를 발생시키고 클라이언트는 토큰 갱신 후 재연결합니다.
