# Shared 경계 리팩터링 테스트 시나리오

## 1. 목적

`shared`가 feature를 참조하던 경로를 제거한 뒤 기존 동작이 유지되는지 검증한다.

이번 변경은 기능 추가가 아니라 파일 소유권과 import 경계를 조정하는 리팩터링이다. 따라서 다음을 중점적으로 확인한다.

- `shared`가 feature 및 앱 조립 계층을 참조하지 않는가
- 약관 동의와 가입 신청 동작이 유지되는가
- 로그아웃 진입점별로 인증·캐시·사용자 상태가 정상 초기화되는가
- 프로필 이미지 선택·업로드 동작이 사용자 및 그룹 화면에서 유지되는가
- SQLite 작업 직렬화와 메시지 로컬 저장소 동작이 유지되는가

## 2. 변경 범위

| 영역 | 변경 전 | 변경 후 | 주요 회귀 위험 |
| :--- | :--- | :--- | :--- |
| 약관 | `shared/constants/terms.ts` | `features/auth/constants/terms.ts` | 기본 동의 상태, 필수 약관 판정 |
| 로그아웃 | `shared/hooks/useLogout.ts` | `features/auth/hooks/useLogout.ts` | 로그아웃 후 캐시·Redux 상태 초기화 |
| 프로필 이미지 | `shared/ui/upload/EditProfile.tsx` | `features/media/components/EditProfile.tsx` | 이미지 선택, 기존 URL 유지, 업로드 |
| SQLite lock | `features/chat/utils/message.ts` | `shared/sqlite/sqliteCall.ts` 내부 | 동시 SQLite 작업 순서, 마이그레이션 |
| 미사용 캐시 훅 | `shared/hooks/useCommonQuery.ts` | 삭제 | 잔여 import 및 타입 오류 |
| feature 진입점 | `index.ts` 공개 API 우선 규칙 | 필요할 때만 선택하고 명시적 경로 허용 | barrel 순환 의존, 잘못된 import |

## 3. 검증 상태 기준

- `통과`: 현재 작업에서 실행하여 성공을 확인함
- `실패`: 실행했으나 기대 결과와 다름
- `미실행`: 기기, Firebase 또는 사용자 조작이 필요하여 아직 확인하지 않음

## 4. 정적 검증

### STATIC-01 Shared 역참조 검사

- 우선순위: 필수
- 상태: 통과
- 확인 대상: `app/shared/**/*.{ts,tsx}`
- 실행 예시:

```powershell
rg -n "@app/features|@features|features/" app/shared --glob "*.ts" --glob "*.tsx"
rg -n "@app/(bootstrap|navigation|layout|store)" app/shared --glob "*.ts" --glob "*.tsx"
```

- 기대 결과: 검색 결과가 없어야 한다.

### STATIC-02 삭제·이동 경로 잔여 참조 검사

- 우선순위: 필수
- 상태: 통과
- 확인 대상:
  - `@app/shared/constants/terms`
  - `@app/shared/hooks/useLogout`
  - `@app/shared/hooks/useCommonQuery`
  - `@app/shared/ui/upload/EditProfile`
- 기대 결과: 기존 shared 경로를 import하는 코드가 없어야 한다.

### STATIC-03 대상 ESLint

- 우선순위: 필수
- 상태: 통과
- 확인 대상: 이번 리팩터링으로 추가·수정된 TypeScript 및 TSX 파일
- 기대 결과: ESLint 오류가 없어야 한다.

### STATIC-04 TypeScript 검사

- 우선순위: 필수
- 상태: 통과
- 실행 명령:

```powershell
node node_modules\typescript\bin\tsc --noEmit
```

- 기대 결과: 타입 오류 없이 종료되어야 한다.

### STATIC-05 Diff 형식 검사

- 우선순위: 필수
- 상태: 통과
- 실행 명령:

```powershell
git diff --check
```

- 기대 결과: 공백 오류와 충돌 표시가 없어야 한다.

## 5. 가입 및 약관 시나리오

### AUTH-01 가입 화면 초기 상태

- 우선순위: 필수
- 상태: 미실행
- 사전 조건: 로그아웃 상태에서 가입 화면 진입
- 절차:
  1. 가입 화면을 연다.
  2. 이용약관과 개인정보 수집·이용 항목이 표시되는지 확인한다.
  3. 아무 약관도 선택하지 않은 상태에서 가입 버튼 상태를 확인한다.
- 기대 결과:
  - 약관 두 항목이 정상 표시된다.
  - 필수 약관에 동의하기 전에는 가입을 진행할 수 없다.

### AUTH-02 개별 약관 확인 및 동의

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. 각 약관의 상세 버튼을 누른다.
  2. 약관 제목과 내용이 표시되는지 확인한다.
  3. `동의하기`를 누른다.
- 기대 결과:
  - 선택한 약관의 상세 내용이 표시된다.
  - 동의 후 해당 체크 상태만 갱신된다.

### AUTH-03 전체 동의 토글

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. `전체동의`를 선택한다.
  2. 모든 약관이 선택되는지 확인한다.
  3. `전체동의`를 다시 선택한다.
- 기대 결과:
  - 모든 약관이 선택된 경우 가입 버튼이 활성화된다.
  - 전체 해제 후 다시 비활성화된다.

### AUTH-04 약관 동의 후 가입 신청

- 우선순위: 필수
- 상태: 미실행
- 사전 조건: 신규 가입에 사용할 수 있는 이메일 준비
- 절차:
  1. 필수 입력값과 약관 동의를 완료한다.
  2. 가입을 요청한다.
- 기대 결과:
  - Firebase Auth 사용자가 생성된다.
  - 약관 동의 상태가 가입 가능 여부를 정상적으로 제어한다.
  - 가입 신청 완료 안내가 표시된다.

약관 동의 기록의 서버 저장은 현재 가입 payload 계약에 포함되지 않으므로 이번 리팩터링 검증 범위에서 제외한다.

## 6. 로그아웃 시나리오

### LOGOUT-01 앱 헤더에서 취소

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. 로그인 상태에서 앱 헤더의 로그아웃 버튼을 누른다.
  2. 확인창에서 `취소`를 선택한다.
- 기대 결과: 로그인 및 현재 화면 상태가 유지된다.

### LOGOUT-02 앱 헤더에서 로그아웃

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. 앱 헤더에서 로그아웃을 확정한다.
  2. 인증 화면으로 전환되는지 확인한다.
- 기대 결과:
  - Firebase 인증 세션이 종료된다.
  - React Query 캐시와 Redux 사용자 상태가 초기화된다.
  - 다음 사용자 로그인 시 이전 사용자 데이터가 노출되지 않는다.

### LOGOUT-03 프로필 메뉴에서 로그아웃

- 우선순위: 필수
- 상태: 미실행
- 절차: 프로필 메뉴에서 로그아웃을 확정한다.
- 기대 결과: `LOGOUT-02`와 동일한 정리 동작이 수행된다.

### LOGOUT-04 차단 계정 자동 로그아웃

- 우선순위: 높음
- 상태: 미실행
- 사전 조건: `reject` 또는 `stop` 상태의 테스트 계정
- 절차: 해당 계정으로 인증 후 프로필 로딩을 진행한다.
- 기대 결과:
  - 접근 제한 안내가 표시된다.
  - 인증 세션, 캐시, Redux 사용자 상태가 초기화된다.

### LOGOUT-05 회원 탈퇴 후 로그아웃

- 우선순위: 높음
- 상태: 미실행
- 사전 조건: 탈퇴 가능한 일반 테스트 계정
- 절차: 회원 탈퇴를 확정한다.
- 기대 결과:
  - 계정 삭제 성공 안내가 표시된다.
  - 로그아웃 정리 동작 후 인증 화면으로 전환된다.

## 7. 프로필 이미지 시나리오

### MEDIA-01 이미지 선택 취소

- 우선순위: 높음
- 상태: 미실행
- 절차:
  1. 프로필 이미지 편집 버튼을 누른다.
  2. 이미지 선택 화면에서 취소한다.
- 기대 결과: 기존 이미지와 폼 상태가 유지된다.

### MEDIA-02 사진 권한 거부

- 우선순위: 높음
- 상태: 미실행
- 사전 조건: 사진 접근 권한 미허용
- 절차: 프로필 이미지 편집 버튼을 누르고 권한을 거부한다.
- 기대 결과:
  - 권한 안내가 표시된다.
  - 앱이 종료되거나 로딩 상태에 고정되지 않는다.

### MEDIA-03 가입 프로필 이미지 업로드

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. 가입 화면에서 이미지를 선택한다.
  2. 필수 입력과 약관 동의 후 가입한다.
- 기대 결과:
  - 선택한 이미지 미리보기가 표시된다.
  - 업로드된 URL이 신규 사용자 프로필에 저장된다.

### MEDIA-04 기존 사용자 프로필 유지 및 변경

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. 기존 프로필 이미지를 변경하지 않고 사용자 정보를 저장한다.
  2. 다시 진입하여 새 이미지를 선택하고 저장한다.
- 기대 결과:
  - 변경하지 않은 경우 기존 원격 URL이 유지된다.
  - 변경한 경우 새 URL로 교체된다.

### MEDIA-05 관리자 사용자 편집

- 우선순위: 높음
- 상태: 미실행
- 절차: 사용자 관리 모달에서 대상 사용자의 이미지를 변경하고 저장한다.
- 기대 결과: 대상 사용자에게 새 프로필 이미지가 저장된다.

### MEDIA-06 그룹 생성 및 편집

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. 이미지가 있는 그룹을 생성한다.
  2. 기존 그룹의 이미지를 변경하지 않고 저장한다.
  3. 새 이미지를 선택하여 다시 저장한다.
- 기대 결과:
  - 그룹 생성 시 업로드 URL이 저장된다.
  - 변경하지 않은 기존 URL은 유지된다.
  - 변경한 이미지는 새 URL로 교체된다.

## 8. SQLite 및 채팅 시나리오

### SQLITE-01 앱 시작 시 메시지 스키마 확인

- 우선순위: 필수
- 상태: 미실행
- 사전 조건: 기존 메시지 DB가 있는 기기 또는 에뮬레이터
- 절차: 앱을 완전히 종료한 후 다시 시작한다.
- 기대 결과:
  - 메시지 스키마 확인·마이그레이션이 오류 없이 끝난다.
  - 기존 로컬 메시지가 유지된다.

### SQLITE-02 채팅방 메시지 조회 및 저장

- 우선순위: 필수
- 상태: 미실행
- 절차:
  1. 기존 채팅방에 진입한다.
  2. 이전 메시지를 조회한다.
  3. 새 텍스트 메시지를 전송한다.
  4. 채팅방을 나갔다가 다시 진입한다.
- 기대 결과:
  - 이전 메시지와 신규 메시지가 정상 노출된다.
  - SQLite lock 이동 전과 동일하게 로컬 저장 및 조회가 동작한다.

### SQLITE-03 메시지 재동기화

- 우선순위: 높음
- 상태: 미실행
- 절차: 프로필 메뉴에서 메시지 재동기화를 실행한 뒤 채팅방에 다시 진입한다.
- 기대 결과:
  - 로컬 메시지 초기화가 완료된다.
  - 서버 메시지가 다시 동기화된다.
  - SQLite busy, locked 또는 table 관련 오류가 발생하지 않는다.

### SQLITE-04 초기화와 조회의 연속 실행

- 우선순위: 높음
- 상태: 미실행
- 절차:
  1. 메시지 재동기화를 실행한다.
  2. 완료 직후 여러 채팅방을 연속으로 진입한다.
- 기대 결과:
  - SQLite 작업이 요청 순서대로 처리된다.
  - 초기화 중 조회로 인한 충돌이나 앱 종료가 발생하지 않는다.

## 9. 완료 기준

- 모든 정적 검증이 통과한다.
- 필수로 표시된 수동 시나리오가 Android 또는 iOS 개발 빌드 중 최소 한 환경에서 통과한다.
- Firebase Auth, Firestore, Storage와 SQLite에 새로운 오류 로그가 발생하지 않는다.
- 기존 데이터가 삭제되거나 다른 사용자에게 노출되지 않는다.

## 10. 이번 작업에서 실행하지 않은 검증

- Android/iOS 앱 빌드
- 실제 기기 또는 에뮬레이터 수동 테스트
- Firebase Auth, Firestore, Storage 연동 테스트
- 전체 Jest 테스트

수동 검증을 수행한 뒤 각 시나리오의 상태와 테스트 환경을 이 문서에 기록한다.
