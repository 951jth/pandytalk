# Feature 브랜치 기반 PR 검토·병합 규칙

## 1. 브랜치 운영

- main: 검토와 검증을 마친 변경을 병합하는 기준 브랜치
- feature/<작업명>: 하나의 목적을 가진 변경을 진행하는 작업 브랜치
- develop: 새 작업의 중간 통합 브랜치로 사용하지 않음

feature 브랜치는 최신 main에서 생성하고, PR의 병합 대상은 main으로 지정합니다.
하나의 PR에는 함께 검토하고 배포할 수 있는 범위의 변경을 담습니다.
이 방침은 앞으로의 작업에 적용하며, 기존 develop 브랜치를 삭제하거나 미병합 변경을 자동 이전하지 않습니다.

## 2. 리뷰 진행

feature 브랜치 작업 → main 대상 PR 생성 → Codex 리뷰와 PR CI 실행 → 지적 내용의 타당성 확인 → 같은 브랜치에서 수정 → 최신 변경의 리뷰·CI 확인 → 사용자 직접 병합

Codex 리뷰와 GitHub Actions는 별도 검사이며 동시에 실행될 수 있습니다.
Codex의 Completed는 타입 체크나 테스트 성공을 의미하지 않습니다. CI 워크플로우는 Codex 실행 순서를 제어하지 않습니다.

추가 커밋이 생기면 이전 리뷰 이후의 변경을 다시 확인합니다.
자동 재리뷰 여부는 실제 Codex 설정을 확인하고, 필요하면 최신 커밋에 대한 리뷰를 다시 요청합니다.

## 3. AI 리뷰 결과의 검증 기준

- 지적한 문제가 실제 코드와 호출 흐름에서 발생하는지 확인합니다.
- 발생 조건과 사용자·데이터에 미치는 영향을 확인합니다.
- 제안을 수용·수정·제외한 이유를 PR에 기록합니다.
- 실행하지 못한 검증은 미검증으로 남깁니다.

세부 검토 절차와 변경 영역별 기준은 [코드 리뷰 규칙](../.agent/workflows/code-review.md)을 따릅니다.
리뷰 요청만으로 소스 수정·커밋·push·머지·빌드·배포를 실행하지 않습니다.

## 4. CI 통과 조건과 main 병합 기준

- main 대상 PR에서 변경 경로와 관계없이 CI를 실행합니다. 새 커밋이 PR에 추가돼도 재실행합니다.
- Lint, Typecheck, Unit Tests를 독립적으로 실행합니다. 하나가 실패해도 다른 검사 결과를 확인할 수 있습니다.
- 최종 `Lint, Typecheck and Test` 검사는 항상 실행하며, 모든 검사가 성공한 경우에만 통과합니다. 실패·취소·생략은 통과로 처리하지 않습니다.
- 리뷰 이후 추가된 변경까지 검토하고, 최신 PR 커밋의 필수 CI가 통과했는지 확인합니다.
- 발견된 문제의 처리 결과와 변경에 필요한 기능 실행·호환성 확인 결과를 검토합니다.
- 남은 미검증 항목과 배포 시 주의점을 확인합니다.

main 변경을 feature 브랜치에 반영하거나 충돌을 해결했다면, 그 과정에서 달라진 코드도 검토하고 CI 결과를 다시 확인합니다.
최종 병합은 사용자가 직접 결정합니다.

## 5. GitHub에서 반드시 적용할 설정

워크플로우 파일이나 이 문서만으로는 머지를 차단할 수 없습니다.

1. 저장소 Settings → Branches → main 대상 보호 규칙을 생성하거나 수정합니다. Rulesets를 사용한다면 main 대상 브랜치 ruleset에 동일한 조건을 적용합니다.
2. Require a pull request before merging을 활성화합니다.
3. Require status checks to pass before merging을 활성화하고 `Lint, Typecheck and Test`를 필수 검사로 선택합니다. 해당 검사 이름이 없으면 워크플로우를 PR에서 한 번 실행한 뒤 선택합니다.
4. Require branches to be up to date before merging을 활성화합니다.
5. 관리자도 우회하지 못하도록 Do not allow bypassing the above settings를 활성화합니다. Rulesets에서는 우회 허용 대상을 비워둡니다.
6. 실패한 CI가 있는 PR의 머지가 차단되는지 확인합니다. Codex 리뷰 내용은 머지 전에 직접 확인합니다.

## 6. 병합 이후 확인

main push의 기존 경로 조건과 배포 대상은 유지합니다.
EAS Update는 최종 CI 성공 후 main push에서만 실행하며, PR 검증 통과와 배포 성공은 구분합니다.

- 브랜치 보호와 자동 재리뷰의 실제 설정을 확인하고, 문서에 적힌 규칙만으로 적용됐다고 판단하지 않습니다.
- 네이티브 변경은 OTA 호환성을 별도로 검토하며, CI 성공만으로 자동 차단이나 배포 안전성을 보장한다고 판단하지 않습니다.
